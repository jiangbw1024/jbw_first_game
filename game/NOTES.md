> 每个概念都按同一个套路组织：**没有它会怎样 → 它怎么解决 → 什么时候会踩坑**。

## S0 · 工程与场景树

### 1. 一个 Godot 工程由什么构成

```
project.godot     工程的"身份证"：名字、入口场景、渲染后端、输入映射
scenes/*.tscn     场景文件（纯文本，可 diff）
scripts/*.gd      GDScript 代码
.godot/           引擎自动生成的导入缓存（不要提交到 git）
```

**为什么是纯文本**：Unity 的场景是 YAML + 二进制混合、Unreal 是二进制资产，改动难以逐行审查。Godot 全部存成文本，能用 git diff、能手写、能被工具/AI 直接生成 —— 这对学习和协作是巨大优势。

### 2. Node（节点）· Scene（场景）· Instance（实例）三者的关系

| 概念 | 是什么 | 类比 |
|---|---|---|
| **Node** | 引擎提供的最小功能单元：能渲染的、能碰撞的、能播声音的、能装 UI 的 | 一块块乐高零件 |
| **Scene** | 一棵节点树，存成 `.tscn` 文件，可被整体复用 | 拼好的乐高小车（说明书） |
| **Instance** | 把 Scene 放进另一个场景后产生的**活的副本** | 按说明书搭出来的真车 |

关键点：**场景可以无限嵌套**。`world.tscn` 里放一个 `player.tscn` 的实例，玩家场景里又放了相机和模型的实例。这是 Godot 最核心的组织方式 —— 你后面会看到"联机时每个玩家是一个 player.tscn 的实例"。

### 3. 场景树（SceneTree）与节点生命周期

- 引擎启动 → 加载 `run/main_scene` → 挂到根节点 `root` 下 → 形成**场景树**
- 常用回调的执行顺序：`_init()` → `_enter_tree()` → `_ready()` → 每帧 `_process(delta)` / 每物理帧 `_physics_process(delta)`
- `_ready()` 只在**首次进入场景树**时调用一次，且是"子节点先就绪、父节点后就绪"（自底向上）
- 所以：**在 `_ready()` 里访问子节点是安全的，访问兄弟/父节点要小心**

⚠️ 坑：`_process` 跟帧率走（帧率越高调用越多），`_physics_process` 固定 60 次/秒。**凡是影响物理和位置的逻辑必须放 `_physics_process`**，否则高刷屏上角色会走得更快。这条在 S2、S3 会反复用到。

### 4. 为什么入口脚本挂在根节点上

`world.gd` 挂在 `World`（Node3D）上，它将来要负责：初始化世界、启动网络监听、管理玩家实例的增删。**根节点是"世界的管理者"**，不参与具体表现 —— 具体表现交给子节点。这种"管理者/表现者分离"是后面扩展到多房间时能平滑演进的前提。

## S1 · 3D 世界

### 1. 3D 坐标系与"看不见的运动"

Godot 用右手系、Y 轴朝上：**+X 右、+Y 上、+Z 朝向屏幕外（即"前方"的反方向）**。相机默认看向 -Z。

关键认知：**人靠参照物感知运动**。一片纯色地面上走 10 米和 100 米，画面几乎一样；这也是为什么联机调试必须有参照柱 —— 否则你根本看不出别人是平滑移动还是瞬移。

### 2. 网格（Mesh）与材质（Material）是两回事

| | 是什么 | 类比 |
|---|---|---|
| **Mesh** | 顶点的集合，决定**形状** | 石膏像的模具 |
| **Material** | 光怎么打在表面上，决定**外观** | 涂在上面的漆 |

所以"同一个网格换材质"= 同一个形状换个涂装。S1 里 14 根柱子共用一个 `BoxMesh` + 一个 `StandardMaterial3D`，只靠 `scale` 拉出不同高度。

⚠️ 性能常识：**资源要复用**。每根柱子各 new 一个材质，显存里就躺 14 份相同数据，引擎还要为每份单独排序切换。这就是"资源共享"在游戏里的真实意义。

### 3. 光照与阴影是有成本的

- `DirectionalLight3D` 模拟太阳：方向固定、距离无限远，只用一个节点照亮全场
- **阴影最贵**：每盏投影灯都要把场景从光源视角再画一遍。`directional_shadow_max_distance` 就是在限制"多远处还在算阴影"
- `WorldEnvironment` 负责天空（`ProceduralSkyMaterial`）与雾。雾不只是好看 —— 它能把渲染距离的边界藏起来，是开放世界最廉价的美术手段

### 4. 为什么要用着色器画网格

地面网格用 `shaders/grid.gdshader` 实时算，而不是贴一张网格图：

- 零资源依赖（不用纹理文件）
- 无限分辨率（贴图放大到 1 米内必糊，算出来的线永远锐利）
- `fwidth` 让线的宽度随"当前像素覆盖多大世界区域"自动变化，远处自动淡出，不产生摩尔纹

顺便理解了材质的本质：`ALBEDO`（反射什么颜色）+ `ROUGHNESS`（多粗糙），光照乘以这些参数才是最终像素。

### 5. 球坐标相机

相机不在世界中心乱放 xyz，而是存 **偏航（yaw）+ 俯仰（pitch）+ 距离（distance）**，再用三角函数换成直角坐标。好处：鼠标左右拖只改偏航、上下拖只改俯仰，互不干扰；要"绕角色转"时也只需要改这三个数。S2 的第三人称相机会沿用同一套思路。

## S2 · 角色控制

### 1. CharacterBody3D vs RigidBody3D —— 选错会做不成游戏

| | 谁说了算 | 适合 |
|---|---|---|
| **RigidBody3D** | 物理引擎。你只能施加力，它决定怎么动 | 被炸飞的桶、滚落的石头、布娃娃 |
| **CharacterBody3D** | 你。你直接设 velocity，引擎只负责"别穿墙" | 玩家、NPC、有操控感的载具 |

玩家必须用 `CharacterBody3D`：玩家要求"按 A 就立刻向左"，而真实物理里加速需要力、转向有惯性 —— 手感会变成一坨漂移的果冻。**游戏手感优先于物理真实**，这是行业共识。

### 2. move_and_slide() 到底做了什么

它不是"位移"，而是三步：

1. 按 `velocity` 移动
2. 和场景里的碰撞体求交
3. 被挡住的位移**沿墙面滑动**（而不是硬停）

第 3 步就是"贴墙滑行"的手感来源。如果自己写 `position += velocity * delta`，撞墙会直接卡死。

⚠️ 它**不会**自动加重力，重力必须你自己写（`velocity.y -= GRAVITY * delta`）。

### 3. 为什么必须写在 _physics_process

`_process` 跟渲染帧率走（60/120/144Hz 不定），`_physics_process` 固定每秒 60 次。

移动写在 `_process` 里的后果：144Hz 屏幕上角色移动速度变成 60Hz 的 2.4 倍。**凡是影响位置与碰撞的逻辑，一律 `_physics_process`。**

### 4. 网格 ≠ 碰撞体（新手第一大坑）

`MeshInstance3D` 只是"看起来有形状"，物理系统完全不知道它存在。所以：

- 地面要有 `StaticBody3D + CollisionShape3D`，否则玩家直接穿过掉进虚空
- 每根参照柱也要有碰撞体

⚠️ 另一个坑：**别给物理体加非等比 scale**。碰撞形状要直接设成真实尺寸，靠 scale 拉伸物理体会产生各种诡异结果（穿模、卡角）。

### 5. 输入映射（InputMap）而不是硬编码按键

代码里永远只问"`move_forward` 被按下了吗"，不问"W 被按下了吗"。

好处：改键、手柄、多套操作方案都只需要改配置。写死在代码里，玩家永远改不了键。

⚠️ 实测细节：**Godot 编辑器保存时会重写 `project.godot`，手写注释会丢失**（它只保留非默认值）。所以工程文件里的注释是"给人看的临时说明"，别指望长期存在。

### 6. 第三人称相机 = 挂在角色身上的吊臂

- 左右转：转**角色本身**（连带相机）—— 相机不是独立飞行的
- 上下转：只转**相机吊臂**（`CameraPivot`），角色不俯仰，否则会斜着走路
- 相机放在角色本地 +Z 4.2 米处（Godot 里角色前方是 -Z，所以 +Z 是背后）

**父子变换继承**在这里发挥作用：角色移动，相机自动跟随，不需要一行"跟随代码"。

### 7. 加速曲线 = 手感

`speed` 直接赋值给 `velocity` 会瞬间满速、瞬间停住，像塑料块漂移。用 `move_toward` 逐渐逼近目标速度，起步和刹车才有重量感。后面调手感，基本都在调 `ACCELERATION` 和 `SPRINT_SPEED`。

## S3 · 联机同步（核心）

### 1. 为什么用 UDP 而不是 TCP

| | TCP | UDP（ENet） |
|---|---|---|
| 丢包 | 重传，**后到的包必须等前面的** | 直接丢，下一帧补上 |
| 延迟 | 一丢包就"卡一下" | 恒定轻微抖动 |
| 适合 | 聊天、建造、交易 | 位置、朝向、射击 |

**关键认知**：玩家宁可要"偶尔丢一帧位置"，也不要"画面整体卡住 200ms"。TCP 的有序性在游戏里是负担 —— 一个旧的位置包迟到了，它已经没用了，强行等它只会让画面倒退。

所以我们的架构里：位置走 `unreliable_ordered`，将来的聊天/建造走 `reliable`。

### 2. peer_id：联机世界的身份证

- 服务端固定是 **1**
- 每个客户端连上后被分配一个唯一 id（实测拿到的是 `1335157029` 这种大数）
- 用途：认出"哪个玩家是我"、RPC 寻址、权限判定

我们把 `peer_id` 直接当**节点名**（`Players/1335157029`），好处是两端路径天然一致，RPC 可以直接按节点寻址，不用额外维护映射表。

### 3. 服务器权威：联机的底线

**错误做法**（新手默认会这么写）：客户端算好位置，`rpc("set_position", pos)` 告诉服务器。
**后果**：任何人改一行坐标就能飞天遁地，服务器只是个转发器。

**正确做法**（我们用的）：
```
客户端：rpc_id(1, "_receive_input", dir, yaw, sprint, jump)   ← 只上报"意图"
服务器：自己算位置 → Synchronizer 广播结果
```

**两道反作弊闸门**（就在 `player.gd` 里，很容易漏）：
1. `if multiplayer.get_remote_sender_id() != peer_id(): return` —— 只接受节点主人发来的输入，否则谁都能操控别人
2. `_input_dir = dir.limit_length(1.0)` —— 不信客户端给的数值，钳到合法范围，否则发 `Vector2(999,999)` 就能加速

### 4. MultiplayerSpawner：生成也由服务器说了算

**为什么不能让各端自己生成**：A、B 都各自 `add_child` 一个玩家，结果是谁也不知道对方存在，出生点、名字、顺序全不一致。

**Spawner 做的事**：服务器往 `Players` 容器里加节点 → 自动在所有端复制出同名同位置的副本。

**代价**：生成/销毁完全由服务器主导，客户端想"本地预生成一个占位"得自己额外写。

### 5. MultiplayerSynchronizer：它替你做了什么，又藏起了什么
**做了什么**：按 `replication_config` 里的属性列表（我们配了 `position` + `rotation`），以 `replication_interval = 0.033`（约 30 次/秒）从**权威端**发往其他端，并在接收端做平滑。

**藏起了什么**（出问题时你会一脸茫然的原因）：
- **带宽**：每玩家每秒 30 次 × (position 12B + rotation 12B)。3 个玩家 ≈ 2KB/s，30 个玩家 ≈ 20KB/s —— 小规模没问题，这就是为什么"开放世界要分区块兴趣管理"
- **延迟**：你看到的别人，是 **RTT/2 + 33ms** 之前的他
- **没有插值缓冲调节**：想要更平滑或更跟手，得自己去动 `replication_interval` 和接收端的插值

### 6. @rpc 的三个维度（四个"模式"其实是三个正交选项）

| 维度 | 取值 | 含义 |
|---|---|---|
| **谁可以调用** | `"authority"`（默认） / `"any_peer"` | 默认只有权威端能调；`any_peer` 允许任何人调（**必须自己校验来源**） |
| **在哪执行** | `"call_remote"`（默认） / `"call_local"` | 默认只在对端执行；`call_local` 本地也执行一遍 |
| **传输保证** | `"reliable"`（默认） / `"unreliable"` / `"unreliable_ordered"` | 位置用后者，聊天/建造用前者 |

我们用的 `@rpc("any_peer", "call_remote", "unreliable_ordered")` 读作：
"任何人可以调 → 但我不校验就危险" + "只在对端跑，本地不重复执行" + "丢了就丢了，按顺序补"。

### 7. 缺的那一环：客户端预测（下一步要补的课）

现在本地玩家也走"上报 → 服务器算 → 同步回来"，所以在真实网络下**你会感觉自己在拖影**（LAN 上只有几毫秒，感知不到；公网 100ms 就很明显）。

解法三层，按复杂度递增：

1. **本地预测**：自己立刻按输入移动，服务器结果回来再"对账"（误差小就别动，误差大才拉回）
2. **实体插值**：别人的位置在两次快照间平滑过渡（Synchronizer 已做了一部分）
3. **延迟补偿**：射击类游戏才需要，回溯到"你开火那一刻"的世界状态

**这正是"服务器权威"的代价** —— 安全换来的延迟，必须用预测还一部分回去。

### 8. 本次实测记录

```
主机自测：起点 z=2.364 → 终点 z=-7.636    （2 秒走 10 米，5 m/s ✓）
客户端：  起点 z=2.839 → 终点 z=-7.161    （同样 10 米 ✓）
服务端看到：玩家 1（我）+ 玩家 587268126（远端）
客户端看到：玩家 1（远端）+ 玩家 587268126（我）
```

链路验证完整：`输入 → RPC → 服务器模拟 → Synchronizer → 回到客户端`。

### 9. 踩坑记录：主机是"双重身份"（真实 bug）

第一版 `_physics_process` 写成了这样：

```gdscript
if multiplayer.is_server():
    _simulate(delta)
elif is_local():
    _send_input()      # ← 主机的输入永远到不了这里
```

**症状**：客户端能走，主机动不了。

**原因**：`is_server()` 和 `is_local()` **不是互斥关系**。主机既在跑服务器，又是玩家本人 —— `if/elif` 把两个重叠的身份当成了二选一，结果主机的输入根本没被采集。服务器在等一份永远不会通过 RPC 到达的输入（因为主机不需要给自己发 RPC）。

**正确写法**：

```gdscript
if multiplayer.is_server():
    if is_local():
        _apply_local_input()   # 主机：本地直接读输入
    _simulate(delta)
elif is_local():
    _send_input()              # 纯客户端：上报意图
```

**教训**：联机代码里最常见的 bug 不是"网络不通"，而是**把重叠的角色当成了互斥的分支**。写判断前先画清楚"此刻我同时是谁"：服务器？客户端？某个玩家的主人？三个问题的答案可以同时为真。

### 10. 另一个坑：连上了 ≠ 进世界了

`create_client()` 返回 OK 只代表"参数没问题"，真正连上是异步的。
第一版漏了监听 `multiplayer.connected_to_server`，导致客户端连上后**菜单一直挂着** —— 那个输入框会抢走键盘事件，表现同样是"进游戏了但动不了"。

**教训**：凡是异步过程，必须有一条明确的"何时算完成"的路径，并且那个时刻要同步更新 UI 状态。

## S4 · 聊天与 HUD

### 1. reliable 与 unreliable：判断的不是"重要性"，是"可替代性"

**两类数据**

| | 状态型（state） | 事件型（event） |
|---|---|---|
| 包的内容 | "我**现在**在 (3.5, 0, 12)" | "我**刚才**说了『快跑』" |
| 包之间关系 | 后来的**覆盖**前面的 | 每个并列且独立 |
| 丢一个的后果 | 少一帧，下个包马上纠正 | 这件事**永远不存在**了 |
| 例子 | 位置、朝向、体力 | 聊天、放方块、开枪、捡物品 |

**口诀的完整版**：

> 这个包丢了以后，**将来会不会有另一个包携带同样的信息**？
> - 会（新状态覆盖旧状态）→ `unreliable`
> - 不会（一次性事件，错过就没了）→ `reliable`

更实用的自问法：**"如果这一条永远收不到，玩家会丢东西吗？"** 不会丢（只是短暂不准）→ unreliable；会丢（少句话、少面墙、血量算错）→ reliable。

**为什么位置不能用 reliable：队头阻塞（head-of-line blocking）**

```
包1(位置@0ms) ✅   包2(位置@33ms) ❌丢   包3(@66ms) 包4(@100ms)
                                        ↑ 全部被扣住，等包2重传
200ms 后才收到包2 → 先把玩家画回 200ms 前，再跳到最新
```

可靠通道会保证顺序，所以丢一个包，**后面所有包都得等它**。等你收到那个旧位置时它已经过期了 —— 这等于"用可靠通道传输过期数据，并强制画面倒退"。所以位置用 reliable 不是更稳，是更糟。

**容易判错的几个**

| 数据 | 判断 | 理由 |
|---|---|---|
| 玩家位置 / 朝向 | unreliable | 下一包覆盖 |
| 血量变化 | reliable | 一次结算，丢了就算错 |
| 聊天 | reliable | 内容独一无二 |
| 放方块 | reliable | 动作丢了那面墙就不存在 |
| 跳跃按键 | unreliable + **输入冗余** | 是事件，但不能用 reliable |

**跳跃的处理**：跳跃是"按下瞬间"的事件，丢了玩家会觉得"按了没反应"。但高频输入不能走 reliable（队头阻塞）。工程做法是**输入冗余**：每个输入包附带"最近 3 帧按过的键"，丢一包下一包还能补上。

**进阶：按"信息性质"拆包，而不是按"对象"打包**

新手常把 `{位置, 血量, 名字}` 打成一个包 —— 位置可丢、血量不可丢，混在一起就只能整体用 reliable，位置被迫跟着队头阻塞。正确做法是分开走不同通道：

```
位置        → unreliable 通道（高频、可丢）
血量/名字/背包 → reliable 通道（低频、不可丢）
```

这就是为什么 `MultiplayerSynchronizer` 里只同步 `position` 和 `rotation`，血量这类状态将来要单独开通道。

### 2. 聊天为什么要经服务器转发（而不是客户端直接广播）

如果客户端能直接 `rpc()` 给所有人，它就能**伪造成任何人的名字**发言 —— 用户看到的是"管理员：所有人把金币转给我"。

正确做法（我们用的）：

```
客户端 --_request_chat("你好")--> 服务器
服务器：sender = get_remote_sender_id()   ← 身份由服务器认定，无法伪造
服务器 --_post_chat(sender, "你好")--> 所有人
```

注意 `_post_chat` 标了 `@rpc("authority", ...)`：**只有权威端（服务器）能调用它**。客户端即使知道这个方法名也调不动。这是靠"RPC 权限"而不是"if 判断"实现的防护，更可靠。

顺带一个细节：服务端会 `text.substr(0, 200)` 裁剪长度，防止有人发一个超长字符串把所有人卡死。

### 3. RTT 怎么量（不需要两台机器对时）

```
客户端：t0 = 本地毫秒时间戳 → 发出去
服务器：原样回传 t0
客户端：rtt = 现在 - t0
```

因为用的是**同一个时钟**（客户端的），所以不需要时间同步。这也是为什么不能"服务器告诉自己现在几点、客户端相减" —— 两台机器的时钟本来就不同。

### 4. 最大的坑：拦掉事件 ≠ 停掉输入

开聊天框时想让角色停下，直觉做法是 `set_input_as_handled()` 把键盘事件消费掉。**没用**。

原因：角色读的是 `Input.get_vector()`，它读的是**设备当前状态**，不是事件流。你把 Enter 事件拦掉了，W 键的"按下状态"依然存在，角色照样往前走。

**必须显式上锁**（`GameState.ui_captures_input`），并且要注意方向：

- ❌ 错误：聊天时"停止发送输入" → 服务器还保存着上一次输入，会一直推着你走
- ✅ 正确：聊天时**发送一个全零输入**，明确告诉服务器"我现在不动了"

**教训**：事件可以被拦截，状态不会。凡是"轮询式"的输入系统，都必须有显式的状态锁。

### 5. 场景实例化：HUD 是一个独立场景

`hud.tscn` 是独立场景，在 `world.tscn` 里以**实例**的形式出现。这正是 S0 讲的 Scene / Instance 关系第一次真正派上用场：

- HUD 可以单独打开调试（F6）
- 以后做"回主菜单"时，HUD 可以整块复用
- 改 HUD 不会碰到世界场景

### 6. 本次实测记录

```
主机:   在线数=2   RTT=主机
        聊天= 我：来自 1 的测试 | 玩家 1851885371：来自 1851885371 的测试
客户端: 在线数=2   RTT=7 ms
        聊天= 玩家 1：来自 1 的测试 | 我：来自 1851885371 的测试
```

两端**身份判定正确**（自己显示"我"，对方显示 peer_id），消息双向到达。

## S5 · 高度图地形

### 1. 高度图到底是什么

**一张二维表格，每格存一个数字 = 那一点的地面高度。** 仅此而已。

```
_heights[j * n + i] = 那张表
        ↓ 拉成曲面        ↓ 交给物理          ↓ 查表插值
    视觉网格 ArrayMesh   HeightMapShape3D    height_at(x, z)
```

我们现在是 160m × 160m、每米一个采样点 → **161 × 161 = 25921 个高度值**。

### 2. 最重要的一条纪律：三者必须同源

视觉、碰撞、查询**必须来自同一份 `_heights`**。

如果网格用 noise 采一次、碰撞又采一次，只要两次采样位置差一点点，就会出现"人半只脚陷进地里"这种灵异现象 —— 而且两边代码看起来都没错，极难排查。

#### 为什么"noise 是确定性的"也不能成为重复调用的理由

诚实的说法是：如果两次调用**完全等价**（同 seed、同坐标算式、同参数、同 falloff），结果必然相同。所以风险不是"这次会算错"，而是下面四件事：

1. **"完全等价"靠人工维持**。真实会发生的漂移：
   - 一处写 `-SIZE * 0.5 + i * STEP`，另一处忘了偏移 → 整张地形平移
   - 一处用 `get_noise_2d`，另一处用 `get_noise_3d(x, 0, z)` → 值完全不同
   - 一处乘了 falloff，另一处忘了 → 碰撞在边缘是高山，视觉是海面
   - 有人给其中一处加了 `* 1.2` 调手感 → 从此永久错位
2. **数据源迟早会换**。今天来自 noise，明天可能是：手绘高度图 PNG、服务器下发的地图、玩家挖改后的增量。数据源一换，两个调用点都要改 —— 漏一个就是幽灵 bug。
3. **性能与内存局部性**。`_heights` 是连续内存一次读到底；重复调 noise 是 5 万次函数调用 + 内部查表插值。地形放大 4 倍时这笔账会变得明显。
4. **可调试性**。有 `_heights` 你就能打印它、画成图、存成 PNG 看这个世界长什么样。数据散在两处计算里，你没法"看到"真相。

**心智模型**：依赖必须是**树状**（一个根 → 多个分支），不能是**平行重复**（两个根各自生长）。树状结构改根时只改一处，且结构上不可能不一致；平行结构靠"写法一致"维系，而没有任何机制保证它一致。

这就是软件工程里 SSOT（单一事实来源）/ DRY 的真实含义：**同一份知识只表达一次**。地形高度的知识，只应该存在 `_heights` 里。

**什么时候重复计算是可以接受的**：纯函数 + 参数完全由同一个常量决定 + 永远不会变。地形显然三条都不满足。

### 3. HeightMapShape3D 的硬约束：间距固定 1 米

`HeightMapShape3D` 的相邻采样点间距被**硬编码为 1 米**，所以 `STEP` 必须等于 1。

想让地形更大，正确做法是**增加顶点数**或**整体缩放**，而不是改 STEP —— 改了就会出现碰撞和视觉错位。

### 4. 为什么会差十几厘米（本次实测）

实测：玩家 y 与 `height_at()` 相差约 **1.05 米**（胶囊半高 0.9 + 0.15 误差）。

原因：**碰撞体用三角形插值，`height_at` 用双线性插值**。在平地上两者一致，在坡地上必然有厘米级差异。

**教训**：用高度查询来放置物体时（树、建筑、道具），要留一点余量往下扎，别假设两者完全相等。

### 5. 为什么必须 LOD（算一下就知道）

| 范围 | 1 米精度顶点数 | 三角形数 |
|---|---|---|
| 160m × 160m | 161² ≈ 2.6 万 | 5.1 万 |
| 2km × 2km | 2001² ≈ **400 万** | 800 万 |

400 万顶点一次性画出来，显卡会跪下。这就是 Terrain3D 那类方案存在的理由：**clipmap LOD** —— 近处 1 米精度、远处 30 米精度，用"距离衰减"换取"能画出 2km"。

### 6. ★ 静态世界对网络的巨大红利

这是选高度图路线最值钱的一点：

- 地形由**固定种子**在每台机器上各自生成（我们 `SEED = 20261111`）
- 服务器**永远不需要同步地形**，只同步"玩家在哪"和"玩家造了什么"
- 反过来，体素世界每挖一格都要广播"哪一格被改了"，带宽和一致性难度高一个量级

**注意**：种子、频率、振幅、顶点数这些参数必须所有端**完全一致**，否则两台机器的地形会长得不一样，玩家会掉进"别人那边不存在的山谷"。

### 7. 相机防穿地形：一条射线就够

从角色头部朝相机方向打射线，撞到东西就把相机拉近：

```gdscript
var query := PhysicsRayQueryParameters3D.create(origin, origin + dir * CAMERA_DISTANCE)
query.exclude = [get_rid()]
var hit := get_world_3d().direct_space_state.intersect_ray(query)
```

没用 `SpringArm3D` 节点，因为它把"相机为什么突然靠近"藏进节点内部；手写 10 行，调试时你随时知道它在算什么。

### 8. 本次实测记录

```
[S5] 地形生成完毕 | 161×161 顶点 | 最高 10.9 m
[S5] 玩家 1 出生在 (-2.6, -0.5, 2.4)
[S5] 玩家 965093525 出生在 (3.3, 3.6, -1.3)
[PROBE] 玩家 1 y=0.57 地面高度=-0.50 落地=true
[PROBE] 玩家 965093525 y=4.65 地面高度=3.60 落地=true
```

两端地形独立生成、完全一致；玩家落在坡地上，没有穿地也没有悬空。

**退役的东西**：`shaders/grid.gdshader` 与 14 根参照柱（它们完成了"让空白世界可感知"的历史使命）。

## S6 · 模块化建造（世界状态同步）

### 1. 这一阶段换了问题的性质

前五个阶段同步的是**状态**（玩家现在在哪），S6 同步的是**事件**（某人在这里放了一块地基）。

| | 状态（玩家位置） | 事件（建造） |
|---|---|---|
| 发送频率 | 每秒 30 次 | 每次操作 1 次 |
| 丢一个包 | 33ms 后自动被新包覆盖 | **这件事永远不存在了** |
| 传输保证 | `unreliable_ordered` | **`reliable`** |
| 需要历史 | 不需要，只要最新 | 需要，因为它**构成世界** |

一句话：位置是"每秒重拍一张照片"，建造是"往账本上记一笔"。**照片可以丢，账不能丢。**

### 2. 三种新机制，缺一个就坏

```
客户端：我按了左键，想放在 (3, 2) 这一格
   ↓  reliable RPC（只说意图，不说结果）
服务器：这个人离得够远吗？这格空着吗？高度多少？
   ↓  reliable 广播（下发裁决后的最终结果）
所有人（含服务器自己）：生成同一个节点
```

**① reliable**：建造用 `unreliable` 的症状是"我放的墙不见了"，且无法补救。

**② 服务器裁决**：客户端连高度都不发——高度由服务器用 `terrain.height_at()` 算。如果让客户端上报高度，改一行代码就能在别人房顶上盖墙。

**③ 加入快照**：事件流只对"当时在线的人"有效。中途进来的人，必须由服务器补发一份完整状态。

### 3. 最容易被忘掉的一条：加入快照

忘了快照的现象是：**中途进服的人看不到之前建的房子，而房主的画面完全正常。**
这种"只有新玩家看得见的问题"在双人测试里几乎不会暴露，等有第三个人加入才会爆。

实现上有个顺序陷阱：**不要在服务器的 `peer_connected` 里推快照。**

```gdscript
# ❌ 客户端那一刻可能还没准备好接收
func _on_peer_connected(id): _snapshot.rpc_id(id, ...)

# ✅ 让需要数据的一方主动请求，顺序永远是对的
func _on_connected_to_server(): rpc_id(1, "_request_snapshot")
```

同理，"快照"是**全量替换**不是"增量补充"。混着用的后果是重复生成同一块（我们的 `_apply_snapshot` 先清空再重建就是这个原因）。

### 4. 网格吸附：把连续世界压成离散格子

```gdscript
_cell = Vector2i(roundi(point.x / GRID), roundi(point.z / GRID))
```

`round` 而不是 `floor` 是关键：`floor` 会让整格向左下偏移半格，相邻两块之间出现固定缝隙。用 `round` 时，落点属于哪个"最近中心"就归哪一格。

**离散化之后，一切都变简单了**：
- 占位判断从"矩形相交检测"变成一次字典查询 `_occupied.has(key)`
- 网络传输从 3 个 float 变成 2 个 int（`cell` + `yaw`）
- 存档从"每个物体的浮点坐标"变成"格子和类型"

### 5. 占位键：为什么地基和墙的键不同

```gdscript
"f:%d:%d"          # 地基占整格，一格只能一块
"w:%d:%d:%d"       # 墙按朝向占，一格能有多面
```

注意墙的 `yaw % 180`：180° 和 0° 在视觉上是同一面墙，不做归一化就会出现"同一位置能叠两面完全重合的墙"。

### 6. 高度为什么由服务器下发（和 S5 的结论不矛盾）

S5 说"地形是确定性的，各端各自生成，不用同步"。那为什么建造时服务器还要把 `base_y` 发下来？

因为**插值差异**：S5 实测过，`height_at`（双线性）和碰撞体（三角形插值）在坡地上差十几厘米。如果各端各自算高度，两块地基在斜坡上的高度就会**因实现细节而不同**——A 看到严丝合缝，B 看到有条缝。

**能用确定性复现的（地形）就不传，会因实现细节漂移的（物体摆放）就传。** 这条判断标准比"能省就省"更可靠。

### 7. `call_local`：忘一次就少一半

```gdscript
@rpc("authority", "call_local", "reliable")
func _apply_place(...)
```

少了 `call_local`，服务器广播时会跳过自己——现象是**客户端看得到房子，主机自己看不到**，而且日志里"放置成功"照样打印。这和 S3 那个"主机是双重身份"的 bug 是同一类错误的两个面孔：**服务器在这套架构里同时是裁判和玩家。**

### 8. 本次实测记录

```
服务端：[S6] 放置 foundation id=1/2/3（t+3s，客户端尚未加入）
        [S3] 玩家 1171761136 加入
        [S6] 放置 wall id=4（t+10s，客户端已在线）
客户端：[S6] 收到世界快照：3 块建筑      ← 补历史
        [S6] 放置 wall id=4（本机共 4 块）← 收实时
        [TEST] 客户端棋子数=4 ids=[1, 2, 3, 4]
```

一次测试同时验证了两条路径：**快照补历史、广播接后续**，两端世界完全一致。

### 9. 现在的边界（诚实的天花板）

- 建筑**不可破坏/不可拆除**？可拆（右键），但没有血量与工具
- 没有**结构强度**：可以在空中悬空叠墙，真实游戏会用"必须连接到地基"来约束
- 没有**持久化**：关服即清零（`_pieces` 只是内存里的字典）
- 没有**兴趣管理**：所有建造广播给所有人。2km 世界里，正确做法是"只同步玩家附近区块的建造"

这四条正好是后面阶段的入口。

## S7 · Terrain3D 大世界（160 米 → 2 公里）

### 1. 换实现之前，先把"契约"抽出来

这一阶段最值得学的东西不是 Terrain3D，而是**动手前做的那一步重构**。

原来 `world.gd` 和 `build.gd` 各自写着一行：

```gdscript
@onready var terrain: Terrain = $Terrain
```

`Terrain` 是手搓地形那个脚本的类名 —— 也就是说，**两个使用方直接绑死在了一个具体实现上**。
现在要把实现换成 Terrain3D（内部结构完全不同：分块、clipmap、GDExtension），
如果不先处理，就得改两个文件里的引用，而且以后每换一次都要改。

做法是把"使用方真正需要的那句话"写成基类：

```gdscript
# terrain_base.gd
class_name TerrainBase
func height_at(_x: float, _z: float) -> float: ...
func playable_radius() -> float: ...
func describe() -> String: ...
func attach_viewer(_node: Node3D) -> void: ...   # 默认空实现
```

然后两个使用方把类型改成 `TerrainBase`（**各一行**），实现随便换：

| | 手搓版 `terrain.gd` | Terrain3D 版 `terrain3d_world.gd` |
|---|---|---|
| 世界大小 | 160 米 | 2048 米 |
| 顶点 | 161×161 一次性 | 1024×1024 + clipmap |
| LOD | 无 | 7 级 |
| 碰撞 | 一个 HeightMapShape3D | 按 region 动态生成 |
| 依赖 | 纯 GDScript | C++ GDExtension |

**判据**：如果你发现"换一个库要改 5 个文件"，那不是库的问题，是缺了这一层抽象。

### 2. Terrain3D 到底替你做了什么

- **clipmap LOD**：不是"一整张网格"，而是以观察者为中心一圈圈往外铺的环，
  远处顶点稀疏。S5 算过：2km 全精度要 400 万顶点，直接卡死。
- **region 分块**：地形按 1024 顶点分块，只渲染/碰撞视野内的块。
- **碰撞生成**：在 `collision_target` 附近按需生成 `HeightMapShape3D`。
- **材质混合**：`auto_slope` 让坡度大的面自动混上第二种材质（草 → 岩），
  省掉手写混合权重。

**代价**：它是编译产物（`.framework`/`.so`），Godot 大版本升级可能要重新编译；
数据不再是我们自己的 `_heights` 数组，改高度要走它的 API。

### 3. 用代码生成地形（不打开编辑器）

```gdscript
var noise := FastNoiseLite.new()
noise.seed = 20261111
noise.frequency = 0.0032
noise.fractal_octaves = 5

var img: Image = noise.get_image(1024, 1024)   # ★ C++ 里生成，几十毫秒
img.convert(Image.FORMAT_RF)                    # 8 位灰度 → 32 位浮点

_terrain.region_size = Terrain3D.SIZE_1024
_terrain.vertex_spacing = 2.0                   # 每顶点 2 米
_terrain.data.import_images(
    [img, null, null],                          # [高度, 控制图, 颜色图]
    Vector3(-1024, 0, -1024),                   # 图片左上角的世界坐标
    -35.0,                                      # 高度偏移
    150.0)                                      # 高度缩放
```

**性能对比（同一张 1024×1024）**

| 写法 | 耗时 |
|---|---|
| GDScript 里 for 循环 `get_noise_2d` + `set_pixel` | 数秒 |
| `noise.get_image()` + `convert()` | **180 毫秒**（含整条导入流程） |

教训：**"这段计算能不能交给 C++ 一次做完"** 是 GDScript 里最划算的性能判断。

### 4. `get_height` 要传世界坐标

```gdscript
_terrain.data.get_height(Vector3(x, 0.0, z))   # ✅ 世界坐标
```

传局部坐标不会报错，只会返回**另一个地方**的地面高度 —— 于是出生点在山上，
建造的地基飘在半空。这类"不报错的错误"最难查，只能靠约定 + 注释。

### 5. 坑一：中文全变成 □（一直存在，这阶段才发现）

Godot 自带字体不含中文字形。修的过程中踩了两次：

| 尝试 | 结果 |
|---|---|
| 项目设置 `gui/theme/custom_font` 指向 `SystemFont` 资源 | 被当成字体**文件路径**加载，空路径 + 刷屏 FreeType 报错 |
| 运行时 `ThemeDB.fallback_font = SystemFont` | 默认主题**自带**字体，优先于 fallback，依旧方块 |
| 按路径 `FontFile.load_dynamic_font("/System/Library/Fonts/Hiragino Sans GB.ttc")` + 赋给 `ThemeDB.get_default_theme().default_font` | ✅ 生效 |

关键认知：**"fallback" 只在"主题里根本没有字体"时才生效**。
默认主题是有字体的，所以要改的是 `default_font`，不是 fallback。

### 6. 坑二：屏幕底部一条灰带（相机贴地）

现象：贴地视角时，屏幕最下面约 15% 是一条灰色横带，取样颜色 (122,127,133) ——
正好落在天空球"地面半球"的渐变中间，说明那个方向**没有渲染地形**。

排查过程（值得记，因为顺序很重要）：

1. 先排除世界几何：从 60 米高空渲染一帧 → 地形连续到地平线，灰带消失
2. 再排除碰撞：从相机向下打射线 → 0.28 米处命中，地形碰撞**存在**
3. 于是结论落在**相机位置**上：`_pitch = -0.25` 这个初始俯角只赋了值，
   从没写回 `pivot.rotation.x` —— 相机其实是水平后拉的，在坡地上离地只剩 0.28 米，
   近裁剪面把脚下那片地面切掉了

修复：`_ready` 里补一行 `pivot.rotation.x = _pitch`。

**试错记录**：第一版修法是"向下打射线，不足 0.9 米就把相机往上抬"，
结果整屏变成清屏色 (77,77,77) —— 因为把相机抬进了山体内部。
**上抬是错的，应该改吊臂角度**。相机问题的通用解法是"改臂角/臂长"，不是"平移相机"。

### 7. 坑三：中文标点会被 bash 当成变量名的一部分

```bash
echo "并发 $PARALLEL，总计 ..."     # ❌ 报 PARALLEL，: unbound variable
echo "并发 ${PARALLEL}，总计 ..."   # ✅
```

多字节的中文标点紧跟在 `$变量` 后面时，bash 会把它算进变量名。
`set -u` 下直接退出。**变量后面紧跟中文，一律加 `{}`。**

## S7.5 · 竖直分层：给网格加第三个坐标

### 1. 现象与定位

反馈是"建造时无法在同一位置重复"。先做的事是**验证平面方向是否通的**：
一次放置 `(-1,4)`、`(0,4)`、`(-1,5)` 三块 —— 全部成功。
说明问题不在 x/z 方向，而在**同一格往上叠**。

根因一句话：占位键只有两个坐标。

```gdscript
"f:%d:%d" % [cell.x, cell.y]      # ❌ 一格只能有一块，第二次必然判定"已占用"
```

**这不是 bug，是数据结构少了维度。** 二维格子只能表达"平面"，
要表达"叠高"就必须加第三维 —— 和 S5 讲体素时是同一个道理。

### 2. 加一维：层（level）

```gdscript
"f:%d:%d:%d" % [cell.x, level, cell.y]              # 地基
"w:%d:%d:%d:%d" % [cell.x, level, cell.y, yaw]      # 墙
```

含义：`level 0` 站在地面，`level N` 站在第 N-1 层的顶面上。

### 3. 高度依然由服务器算（这一点最关键）

客户端只上报 **「哪一格、第几层」**，高度由服务器的 `_floor_y()` 算：

```gdscript
func _floor_y(cell, level) -> float:
    if level <= 0: return terrain.height_at(cell.x * GRID, cell.y * GRID)
    return _tops.get(_support_key(cell, level - 1), NAN)   # 下面那块的顶面
```

`_tops` 是"某格某层的最高顶面高度"。**没有支撑就返回 NAN，放置直接失败。**

如果让客户端报高度，它就能把地板放在半空 —— 这和 S6 讲的距离闸门是同一条原则：
**凡是"世界的状态"，都由服务器裁决；客户端只表达意图。**

### 4. 对准哪里，决定放到哪一层

用命中面的法线判断，这是所有建造游戏的标准交互：

| 射线打到 | 结果 |
|---|---|
| 地形 | 第 0 层，格子由 x/z 取整 |
| 某块的**顶面**（`normal.y > 0.6`） | 同一格，**层 +1** |
| 某块的**侧面** | 同一层，格子沿法线方向挪一格 |
| 某块的底面 | 不处理（不能从地板下面往上塞） |

### 5. 教训：`REACH_UP` 太小会误伤

第一版把"手够得着"设成相对角色中心 1.8 米。结果：
**在地基上放 2.4 米高的墙被拒绝** —— 顶面比角色中心高 1.9 米，差 0.18 米。
改成 2.6 米（约一臂长）后正常。

这类"差一点点"的拒绝最难受：玩家看到预览变红，却不知道为什么。
**判定阈值要按"最常用的操作"来校，而不是按直觉。**

### 6. 连锁拆除：拆底层，上面一起塌

```gdscript
for other_id in _pieces.keys():
    var o = _pieces[other_id]
    if o["cell"] == cell and o["level"] > level:
        _apply_remove(other_id)
```

不做这一步，抽掉地基后上面的墙会**停在半空** —— 看起来像 bug，
本质是"世界不承认重力"。注意这里不需要额外发网络消息：
所有端收到同一条拆除指令后跑同一段确定性代码，结果天然一致。

### 7. 本次实测记录

```
[S7.5] 放置 foundation id=1 格=(-1,4) 层=0
[S7.5] 放置 foundation id=2 格=(-1,4) 层=1
[S7.5] 放置 wall      id=3 格=(-1,4) 层=1
[STACK] 玩家 y=41.11 | 0层地基=true 1层地基=true 1层墙=true 2层墙=false 空中第9层=false
[STACK] 各块底高=["foundation@40.29", "foundation@40.69", "wall@40.69"]
[S7.5] 拆除 id=1 → id=2 → id=3（连锁）
[STACK] 拆掉 0 层后剩余 0 块
```

底高差正好 0.40 = 地基厚度，说明"上一层站在下一层顶面"成立。

### 8. 还没做的（下一步的入口）

- **结构强度**：现在只要"下面有东西"就能放，不判断承重是否合理（一根柱子能托起整栋楼）
- **拆除范围**：连锁是全格塌，真实游戏会做"局部掉落/物理碎块"
- **多层寻路**：楼梯还没有，上二楼只能靠跳

## S8 · 世界基础：程序城镇 / 出生点 / 商店交互

本轮把"骨架"变成"有地方可去的世界"：1 主城 + 2 哨站的程序化城镇、可进入的多层建筑、
多出生点、E 键交互、商店 NPC 与手持武器外观同步。

### 1. 确定性生成：三条纪律

城镇不联网同步几何，各端各算一遍。代价是必须保证**逐位一致**：

1. 唯一随机源 `TOWN_SEED` + 专属 `RandomNumberGenerator`；禁止全局 `randi()/randf()`
2. 生成函数全 `static`、无 `await`、无 `if multiplayer.is_server()`
3. 布局只依赖 `terrain.height_at()`（两端同种子同参数）

**验证方式**：同一份代码连跑两次，`TownGenerator.digest()` 的输出做 diff，必须为空。
这比"两人进去对一眼"可靠得多 —— 后者只能证明"这一次看起来一样"。

### 2. 建筑：视觉合并，碰撞不合并

- 一栋楼 ≈ 50 个盒子 → **合并成 1 个 ArrayMesh**（1 个 draw call），
  但碰撞保留 **N 个 BoxShape3D**（引擎只认独立形状；BoxShape 是最省的形状，别用凸包）
- 基座不是"改地形"，而是从 footprint 最低点往下 0.8 米浇到最高点 +0.2 米 ——
  把坡地包进混凝土。**绝不写 Terrain3D 高度图**，那会引出"地形要不要同步"的地狱问题

### 3. 楼梯为什么是斜坡而不是台阶

`CharacterBody3D` **没有自动上台阶能力**，0.2 米的竖直台阶对它就是一堵墙。
所以碰撞必须是一块 36° 的斜盒子（小于默认 `floor_max_angle` 45°）。
灰盒阶段直接把斜坡当楼梯用；等有美术再换成"视觉台阶 + 隐形斜坡"。

### 4. 真实 bug：门朝向在"世界坐标"还是"局部坐标"

墙是在建筑**局部坐标系**里开洞的，整个建筑再绕 Y 转 yaw。
第一版把"朝广场"的方向直接当成 door_dir 用（世界坐标），结果：
**yaw=0 的楼门是对的，yaw=90 的楼门开到了背面** —— 一半对一半错，最难查。

修法两点：
- 生成时把世界方向 `rotated(UP, -yaw)` 转成局部再定 door_dir
- 取世界坐标时反过来 `rotated(UP, +yaw)`

★ 并且**不要手写 sin/cos 旋转矩阵**：我手写的那份方向反了（Godot 的 `Basis(UP,+r)` 与
"逆时针公式"差一个负号）。统一用 `Vector3.rotated()`，让引擎决定正负。

### 5. 出生点：轮转而不是随机

同时进来的两个人如果各自"随机取一个出生点"，可能抽到同一个 → 出生即重叠。
改成服务器维护 `_spawn_cursor` 轮流分配。首次进主城广场，
之后按 `_last_pos` 就近上次位置（断线那一刻记录，节点 free 之后就问不到了）。

**禁建判断要分两层**：`is_blocked()` = 广场圆 ∪ 压在楼上。
选出生点时只能用"是否压在楼上" —— 出生点本来就设计在广场里，
用 `is_blocked()` 筛选会把所有出生点排除干净（本次实测踩到，表现是"永远只出生在第一个点"）。

### 6. 交互：契约 + 分离的三个信号

```
Interactable（基类）: prompt_text / can_interact / interact
玩家子节点 player_interact: 相机射线 → 最近可交互物 → GameState.set_prompt()
ShopNpc  --shop_requested-->  ShopPanel  --buy_requested-->  ShopService
```

- 射线打 `WORLD | INTERACT`，**不能只打 INTERACT**：否则射线穿墙，站街上能瞄到屋里的 NPC
- 二次距离校验：相机在身后 4.2 米，"相机够得着" ≠ "人够得着"
- 输入锁从裸 bool 改成 `claim_ui/release_ui` 的集合：聊天和商店可能同时开着，
  裸 bool 下关聊天会把商店也放开

### 7. 外观同步：为什么用 RPC 而不是 Synchronizer

| | MultiplayerSynchronizer | RPC（本轮选它） |
|---|---|---|
| 可靠性 | 不可靠通道 + "变更时发一次"，**丢一次就永久不同步** | reliable，一次成功即终态 |
| 新人加入 | 靠 spawn 状态自带 | 需要 `_request_equipment` + 重放 |
| 适合 | 高频连续量（位置） | 低频离散事件（装备、购买） |

**过网的只有一个 int**（item_id），造型由两端查同一张常量表还原 ——
这样"外观不同步"从结构上就不可能发生。

新人重放：`_equipment` 缓存是唯一真相；`_apply_equip` 找不到玩家节点就只写缓存，
`world._on_player_added` 再调 `shop.replay(node)`（幂等）。
覆盖"装备 RPC 比节点复制先到"这个顺序问题。

### 8. 无头探针（本轮最有用的工程习惯）

`-- --selftest <名字>` 跑一条断言链，输出 `[TEST]` 并以退出码表示成败。
这轮靠它抓到了三个"看起来对其实错"的问题：

| 现象 | 真相 |
|---|---|
| 门口有地面 0/10 | 探针从盒子**内部**往下打，`hit_from_inside=false` 所以不命中 → 改用水平穿门测试 |
| 门洞不通 7/10 | 门朝向的世界/局部坐标搞反（真 bug） |
| 测试挂了 9 分钟不退 | 探针脚本解析失败，没人调用 `quit` → 加了 30 秒保险丝 |
| 找不到玩家节点 | 7777 端口被上一个实例占着，`create_server` 失败 → 先 pkill 再跑 |

## S8.5 · 门口：台阶、平台、台阶辅助

真实反馈只有一句：「没给 NPC 的屋子设置台阶和门口，我得跳起来才能交互；有些房子不太好进入」。
修这句话花了六轮排查，每一轮都推翻了上一轮的结论 —— 所以这一节按**排查顺序**写。

### 1. 现象拆解

| 现象 | 真正的机制 |
|---|---|
| 得跳才能进 | 楼板高度 = 地基最高点 + 0.2，坡地上比门外地面高 1-7 米，门口就是一堵混凝土坎 |
| 有些房子进不去 | 两种独立原因：① 门洞被土埋了（门朝上坡）② 门外有土脊/土坎，人走不到台阶底下 |
| 明明有台阶还是上不去 | `CharacterBody3D` **完全没有**台阶攀爬能力，1 厘米的错台也算一堵墙 |

### 2. 第一次修：加门廊（平台 + 台阶 + 雨棚）

`TownBuilding._porch()`：平台把楼板"伸"到墙外，台阶一级级降到地面，雨棚让灰盒楼有了"入口"。

**关键细节：视觉是台阶，脚下踩的是隐形坡道。**
`CharacterBody3D` 上不了竖直台阶，所以碰撞必须是一条连续斜面（26.6°，低于 `floor_max_angle` 45°）。
坡道只做碰撞、不做视觉；台阶只做视觉、不做碰撞（除了每级踏面本身要能站）。

### 3. 第二次修：台阶长度按"沿地面下探"算，不是按落差算

第一版按 `落差 / 踏步高` 算级数，缓坡上是三级小台阶，坡地上直接算出六米长的大楼梯
（实测有一栋楼门离地 5.9 米）。改成沿门外方向每 0.2 米探一次，
找到"坡道面第一次沉到土面之下"的那一点 —— 短、贴地、不会悬空。

### 4. 第三次修：`BuildingSite` —— 把算法收成唯一出处

原来"地基多高/台阶多长"只写在 `TownBuilder`，而选址打分需要同一份算法。
两处各写一遍必然漂移。抽成 `BuildingSite.apply(terrain, spec)`：
**生成器用它打分，建造器用它造楼**，一个函数，两个使用者。

### 5. 第四次修：选址打分（位置 + 门朝向）

有些楼放在 30° 的坡上，基座 8 米厚、门口落差 7 米，**加多少台阶都救不回来**。
在 `_populate` 里对每个建筑试 3 个位置 × 3 个半径 × **4 个门朝向**，取分数最好的。

★ 门朝向比位置更关键：楼板高度由"地基最高点"决定，
**门只有开在坡的上坡侧，落差才小**。门朝下坡 = 把入口开在悬崖上。
朝广场只是好看，所以只给 1.2 米当量加分。

### 6. 第五次修：平台深度自适应（最关键的一层）

前三层结构定下来之后仍然有 6/10 进不去。打剖面才看清真相：

```
d=4.0~6.0  y=46.38   ← 平台（平的，完美）
d=6.4       y=46.38   ← 两级台阶
d=6.8       y=46.22   ← 台阶底
d=7.2       y=47.72   ← ★ 一道 1.5 米高的土脊
d=8.0+      y=45.83   ← 土脊后面又是一个坑
```

**土脊把楼板顶高了，于是"落差"指标只有 0.2 米（看着完美），可人要翻过那道坎才过得来。**
换个指标没用 —— 因为这两个指标被同一道土脊同时骗过。

解法是把结构改成三层：

```
① 楼板 = 楼内最高点与门外最高点里更高的那个 + 0.2   （门不能被土埋）
② 平台 = 往外铺，直到地面离楼板 ≤1 米               （土包直接埋进平台里）
③ 台阶 = 从平台外沿下探，只负责最后那 ≤1 米
```

第一版 ② 写错了：`if edge < best_edge` 取最小 edge —— 那等于**专挑被土埋得最深的地方停下**，
正好挑反。正确做法是 `edge < 0` 时继续往外铺（埋掉它）。

### 7. 第六次修：`StepAssist` —— 给物理层加台阶辅助

几何都对了，玩家还是会被"差一点点"的错台卡住（坡道与地形的接缝、
每一级踏步的边缘）。这是 `CharacterBody3D` 的能力缺失，不是关卡问题。

```gdscript
# 被竖直面挡住 → 抬高 0.35 米试走一步 → 走得通且落点有地 → 落下去
static func try_step(body: CharacterBody3D, step_height: float) -> void
```

写成**静态工具**而不是 player.gd 里的一段，是因为无头探针要用**同一份逻辑**验证可走性。
复制一份就会变成"改了一边忘了另一边"的经典漂移。

### 8. 验收方式也换了一次

前四轮用的是"放一个真胶囊走一遍"。它测出来的是**探针自己的行为**：
会被自身穿透卡住、被贴地吸附影响、被起点位置影响，结果反复误报。
最后换成更朴素的判据：

> 沿门口路径每 0.2 米打一条向下的射线，**相邻两点高差 ≤ 0.3 米** = 人能走上去。

```
[TEST] 门口可走（单步 ≤0.30 米）：10/10 ｜ 最大落差 0.14 米
[TEST] 建筑=10 碰撞盒=703 最少单栋=47 ｜ 门口有地面=10/10 楼梯有碰撞=10/10
```

**教训：当"模拟玩家"的测试反复给出反直觉的结论时，先怀疑测试本身。**
换成直接测几何属性，立刻稳定了 —— 因为"人能不能走"本来就是几何问题。

### 9. 顺带修掉的一个真 bug：楼梯挡住门

内楼梯原先固定放在 -X 侧。门如果开在 -X 面，一进门正前方就是楼梯中段（1.6 米高），
等于进门撞墙。现在 `_stair_x0()` 在 `door_dir == 3` 时把楼梯整个挪到 +X 侧。

### 10. 现在是怎样

- 每栋楼都有：平台（深度按地面自适应）+ 台阶（每级 ≤0.15 米）+ 雨棚
- 每级台阶都有隐形坡道兜底，加上玩家自己的 0.35 米台阶辅助，三重保险
- 选址会挑"门口最平 + 门朝上坡 + 不挤邻居"的位置，所以**有些楼的门不一定朝广场**
  —— 这是刻意的取舍：能不能走进去 > 好不好看
- 商店 NPC 的交互距离从 3.5 放宽到 4.5 米，站在门口就能交易

## S9 · 第一人称与射击手感（AK47）

> 目标：把"能走能捡的沙盒"变成"枪能响、打得爽"的射击游戏。
> 本轮只做 **一把 AK47** —— 一把调透，比三把半成品值钱。

### 1. 相机改造：把"看"和"走"拆开

第一人称不是"把相机往前挪"，而是**拆开两个原本合在一起的职责**：

| | 谁算 | 为什么 |
|---|---|---|
| 视角（yaw/pitch） | **本地、每帧立即** | 转视角等服务器回包 = 鼠标拖着湿海绵 |
| 位移（position/velocity） | **服务器权威** | 否则改客户端就能瞬移穿墙 |

单机时两者都在本地，看不出差别；但代码里必须已经分开，否则开联机是重写。
落点：`player._unhandled_input` 里的 `_local_look` 与 `_physics_process` 里的 `_simulate`。

### 2. 手感不是"一个参数"，是 12 层叠出来的

| # | 层 | 本轮做法 | 少了它会怎样 |
|---|---|---|---|
| 1 | 射速 | `interval = 0.10`（600 RPM） | 连点变成全自动，节奏消失 |
| 2 | 输入缓冲 | 冷却结束前 0.12s 内的点击会补上 | "我明明按了却没反应" |
| 3 | 后坐力（垂直） | 每发抬头 1.05°，10.5°/s 回落 | 枪像钉在墙上 |
| 4 | 后坐力（水平） | 每发随机 ±0.52°，**真的转身体** | 只有直线，没有"要压枪"的感觉 |
| 5 | 扩散 | 基础 0.32° + 连射累积 + 移动/空中惩罚 | 扫射和点射一样准，没有技巧空间 |
| 6 | 枪声 | 程序合成三层（爆裂+轰鸣+尾音） | 像玩具枪 |
| 7 | 枪口火光 | 径向贴图 + 补光 + 0.055s | 夜里开枪像在放幻灯片 |
| 8 | 曳光 | 从**枪口**到命中点，0.075s | 不知道子弹飞哪去了 |
| 9 | 弹壳 | 刚体抛出，2.2s 后回收 | 少了"这是一把机械"的实感 |
| 10 | 击中反馈 | 命中标记 + 血肉/爆头两种音效 + 伤害数字 | 不知道自己打中没有 |
| 11 | 武器摇晃 | 转身滞后 + 走路 bob + 换弹下沉 | 枪像贴在屏幕上的贴纸 |
| 12 | 空仓声 | 空弹匣点击有"咔" | 玩家以为游戏卡了 |

**结论**：任何一层单独做都不明显，**叠起来才叫手感**。

### 3. 后坐力回落为什么不用乘法衰减

```gdscript
_recoil *= 0.9          # ❌ 60Hz 和 144Hz 下每秒衰减量不同
_recoil = move_toward(_recoil, 0.0, deg_to_rad(recover) * delta)   # ✅
```

乘法衰减是"每帧乘一个系数"，帧率越高衰减越快 —— 同一个游戏在别人的机器上手感会变。
**凡是随时间变化的量，都要乘 `delta`。**

### 4. 扩散是"方向扰动"，不是"随机落点"

```gdscript
var r := sqrt(randf()) * spread_rad          # 圆盘内均匀（不开方会挤在中心）
return (dir + right * tan(r) * cos(a) + up * tan(r) * sin(a)).normalized()
```

先随机一个落点再连线是错的：那样散布形状随距离变化，远处会变成一条横线。

### 5. 为什么用 hitscan 而不是抛射物

丧尸在 5–30 米内，弹速 300+ m/s，飞行时间 <0.1s，人眼不可感知；
但抛射物要多一套物理体、多一套碰撞、多一套同步。
**近距离射击用 hitscan 是正解**，狙击/投掷物以后再引抛射物。

### 6. 没有音频素材，就合成一个

枪声的物理构成很固定：

```
爆裂（高通白噪声，0.07s 衰减）+ 轰鸣（低频正弦 95Hz，下滑）+ 尾音（低通噪声，4s 衰减）
```

三层叠起来才有"重量"。三个必须知道的细节：

1. **每次播放随机微调音高**（±5%）—— 否则连发会变成"机关枪复读"，非常假
2. **归一化到同一峰值** —— 不同音效响度差一倍，混在一起像坏了
3. **软削波 `tanh`** —— 直接截断会"炸"，tanh 会把峰值压圆，听起来更厚

无头模式听不到声音，但可以验证"不是静音"：读 16 位采样求峰值。
一个写错的下标会生成全零缓冲区，游戏里表现为"开枪没声音"且**完全不报错**。

### 7. 特效的三个坑（都花了时间）

| 现象 | 根因 | 解法 |
|---|---|---|
| 枪口火光是一块**硬边黄方块** | QuadMesh + 纯色材质 | 程序生成 64×64 径向渐变贴图（`FxTex.radial()`） |
| 血雾只有**零星几个小点** | ① `pow(a, 2.4)` 让只有中心不透明 ② `BILLBOARD_ENABLED` 按节点原点算朝向，侧看变细线 | ① 衰减改成 `pow 1.5` ② 用 `BILLBOARD_PARTICLES` |
| 粒子**时有时无** | `local_coords = false` 时仍按节点包围盒做视锥裁剪 | 设 `visibility_aabb` 为 5×5×5 |

### 8. 两个测试坑（都很有代表性）

**坑一：节点存在 ≠ 物理就绪。**
`add_child` 之后碰撞形状要等下一个 physics frame 才进空间，
这段时间射线什么都打不到。症状：**第一次射击伤害 0，后面正常**。
解法：等两个 `physics_frame` 再开测。

**坑二：坡地上，低处的射线会先撞地形。**
测试瞄"胸口 0.85 米"，8 米外的坡地把射线挡了 → 伤害 0，而瞄头（1.75 米）正常。
看起来像"身体判定坏了"，其实是**关卡几何**问题。
诊断方法：打不中时把射线命中的 collider 名字打出来，一眼就分清了。

# S9.5 · 为什么"模型都很粗糙"，以及它其实不是模型的问题

## 0. 一句话结论

灰盒阶段的画面之所以廉价，**几何面数只占两成**，剩下八成来自三件事：
**没开抗锯齿、材质是纯色、地形贴图尺度错了**。
把这三件修完之后，同一批盒子模型的观感会完全不同 —— 这也是为什么"先做手感、后做美术"是成立的。

## 1. 诊断：粗糙感从哪来

| 症状 | 真正的病根 | 修法 |
|---|---|---|
| 建筑边缘一排台阶 | 没开抗锯齿 | FXAA + debanding |
| 东西像"贴"在画面上 | 没有 SSAO，接触处不发暗 | SSAO |
| 影子几乎看不见 | 环境光太强，把阴影照亮了 | 降 ambient |
| 地上大白斑 | 地形贴图 UV 尺度错了（一张 256px 铺 66 米） | uv_scale 0.015 → 0.22 |
| 枪像塑料玩具 | 纯色材质、方块截面 | 圆柱件 + 4 种材质 + 噪声贴图 |
| 敌人像雪人 | 胶囊 + 球，没有肩线和四肢 | 加外套/手臂/腿，建立剪影 |

**判断顺序很重要**：先怀疑渲染，再怀疑材质，最后才是几何。
因为渲染是全局的（改一行，整个画面变），几何是局部的（改一天，一个模型变）。

## 2. 地形贴图：三个参数必须一起改

```gdscript
_make_texture(name, albedo_freq, uv_scale, gradient, normal_strength)
```

- **uv_scale**：一张贴图在世界上铺多大。`0.22` ≈ 每 4.5 米重复一次。
  设成 `0.015` 就是 66 米重复一次 —— 256 像素摊到 66 米，**一个像素 26 厘米**，
  贴图被放大成大色斑，看起来像塑料布上贴了白纸。
- **albedo 频率要低**：贴图重复得密，图案一旦明显就会看到"同一朵云反复出现"。
  低频噪声只负责大块颜色起伏。
- **法线频率要高**：颗粒感靠它。两者用不同频率，才有"远看自然、近看有细节"的层次。

## 3. 三个难从画面上反推的坑

### 坑一：Terrain3D 的控制图不能传 null

```gdscript
_terrain.data.import_images([height, null, null], ...)   # ← 错
```

控制图决定"每平方米用哪一层材质"。传 null 时它**不会**当成"全用第一层"，
而是**拿高度图本身当控制图** —— 于是地形的高度轮廓被直接翻译成
"这里长草、那里是石头"，平地上出现跟着等高线走的大片灰白斑块。

这个 bug 极难从画面上猜出来。**定位它的方法值得记住**：
把第二层材质临时改成**纯红色**，重跑截图。
斑块变红 → 那一定是第二层材质。一步就把范围从"整个渲染管线"缩到"材质分层"。

### 坑二：控制图的通道顺序是反的

补控制图时想当然写了 `Color(1,0,0,0)`（R = 第一层），结果整片地面全黑。
实际是 **A 通道对应第一层**：`Color(0,0,0,1)` 才正确。

教训：**"权重和为零"会渲染成黑色**，这是一个很好用的信号 ——
看到整片纯黑，先怀疑权重没归一化，而不是怀疑光照。

### 坑三：MSAA 会让方向光阴影整个失效

开 4x MSAA 之后，建筑的投影突然全没了；关掉就回来。
最后抗锯齿改用 FXAA（代价是轻微糊掉高频细节）。

**取舍原则**：阴影对"体积感"的贡献远大于边缘锯齿，
所以宁可要 FXAA + 有阴影，也不要 MSAA + 没阴影。

### 附：自检不要等固定时长

给 AK 加了噪声贴图之后，武器构建慢了半秒，`shoot` 自检的第一发就从
"伤害 34"变成"伤害 0" —— 因为靶子的碰撞体还没进物理世界。
把等待从 0.12s 提到 0.30s 只是治标，**根子在于"等一个时长"本身就是脆的**。
真正该等的是一个**状态**（射线能打中）。

## 4. 枪的做法：剪影 > 倒角

第一人称的枪占屏幕约 1/4，"粗糙"的感受有一半来自它。
但改造的重点不是加面数，而是：

1. **把方块换成圆柱**：枪管、护木、导气管。圆面能接住环境光的连续渐变，
   方块永远有一圈硬边。
2. **补小零件建立轮廓**：准星护翼、扳机护圈、拉机柄、枪口制退器。
   人对"这把枪是什么"的判断来自这些凸起，而不是机匣的曲面。
3. **弹匣用 5 段而不是 3 段**：3 段能看出是折线，5 段就读成弧线。
4. **四种材质分开**：发黑钢（metallic .62 / rough .26）、磨光钢（.75/.36）、
   木（0/.52）、聚合物（0/.62）。之前四种颜色共用一个 metallic，
   所以哪一块看起来都像同一种塑料。
5. **噪声贴图用 NoiseTexture2D**，不要自己 for 循环写像素。
   第一版手写 128×128 循环 ×4 张，光这一项就让出生卡了半秒。
   异步生成 + `color_ramp` 把明暗压到 `(1-contrast)..1` 区间（直接用 0..1 会出黑斑）。

## 5. 新增的自检：`--selftest shot`

```
tools/Godot.app/Contents/MacOS/Godot --path game -- --solo --selftest shot
```

画质这类改动没有数值断言，只能靠看图。所以加了这个用例：
跑 40 帧 → 压平视角、转向最近的靶子 → 读 viewport 存 PNG。

两个细节：
- **不能加 `--headless`**：无头模式没有渲染目标，截出来是空图。
- **要等 `RenderingServer.frame_post_draw`**：否则读到的是上一帧。
- **必须固定视角**：无焦点窗口也会产生鼠标 relative 事件，`_pitch` 早就不是 0，
  同一份代码两次截图会一个朝上一个朝下，没法对比。

## 6. 这一轮的边界

- 敌人还是**静态人形靶**（S10 才换成会动的丧尸）
- 建筑仍是**纯白盒子**：没有窗户/门框/污渍，这是下一个最明显的短板
- 没有贴图资源，所有表面细节都是程序化噪声，**近看会糊**
- 地形只有一层材质，山坡没有裸岩（控制图要按区域刷，不能靠 auto_slope 自动生成）
- 枪没有手部模型，第一人称只看到枪

# S9.6 · 第一人称持枪姿态：为什么"看起来假"

## 1. 一句话

悬空的枪 + 缩得太小 = 一眼读出"这是模型"。
**加上手臂、把枪拉到 30 厘米、让枪管平行视线**，三个动作就把它变回"我在拿这把枪"。

## 2. 三个参数各管什么

```gdscript
const BASE_POS   := Vector3(0.148, -0.118, -0.306)
const VIEW_SCALE := 0.75
const BASE_ROT   := Vector3(0.0, 0.015, 0.0)
```

- **BASE_POS.z** 决定"枪离眼睛多远"。z 从 -0.35 收到 -0.30，透视放大 17%，
  这是"枪看起来有没有分量"最敏感的一个数。
- **BASE_ROT** 越接近 0，枪管越平行于视线 —— 也就是准心指向哪、枪管就指向哪。
  很多人下意识给枪加 yaw 想做出"斜跨"的感觉，结果是枪口和弹道对不上，
  而且看起来像"枪歪了"。真实 FPS 里枪身的斜，是**透视**造成的，不是旋转。
- **VIEW_SCALE** 只是统一缩放，改它要同时改 BASE_POS，否则枪会跑到画面外。

## 3. 手臂的两个致命坑

### 坑一：前臂末端不能靠近相机平面

相机在局部坐标 z = +0.31 处。前臂一旦朝 +Z 延伸过去，
透视会把它放大成一根糊在屏幕中央的粗柱子。我第一次写就成了这样。

**正确做法**：手臂朝**画面左右两侧**（x 方向）跑出视野，z 几乎不变。
让手臂"从画面边缘伸进来"，而不是"从相机里长出来"。

### 坑二：枪托会挡住右手

枪托在握把后方，也就是**更靠近相机**的一侧。
如果枪托和机匣同轴，它会正好遮住握把上的手 —— 画面里只看到一块木头。

真实持枪时枪托抵在右肩，本来就在身体右侧。所以给枪托加 12° 的 yaw 外偏，
既是物理正确的，也顺手解决了遮挡。

## 4. 左手看到的是手背

第一人称看自己的左手托护木，眼睛在手的**右后方**，看到的是手背。
所以：掌心朝上贴护木、手背朝相机、四指从护木**左侧**绕下去。

把手掌摆在护木正下方（我试过），从相机看就是一个肉色方块，没有手指。

## 5. `_limb(a, b, r_a, r_b)`：两点之间放一根锥形圆柱

```gdscript
var y_axis := (b - a).normalized()
var ref := Vector3.FORWARD if absf(y_axis.dot(Vector3.FORWARD)) < 0.95 else Vector3.RIGHT
var x_axis := y_axis.cross(ref).normalized()
var z_axis := x_axis.cross(y_axis).normalized()
mi.transform = Transform3D(Basis(x_axis, y_axis, z_axis), (a + b) * 0.5)
```

要点：
- CylinderMesh 沿 +Y 生长，所以把 **局部 Y 轴对准 a→b**
- 参考向量不能和 y_axis 平行，否则叉积为零（退化）
- **x × y 必须等于 z**，否则 basis 是左手系，模型会被镜像

## 6. 这一版的边界

程序化手在这个精度下就到头了：
- 手指是 6 边圆柱，没有指节、指甲、褶皱
- 没有手腕的骨点过渡，前臂像一根均匀的管子
- 肤色是纯色 + 噪声，没有皮下血色、没有 AO

**要真正接近参考图那种照片级的手，只有两条路**：
① 接入美术做的手部模型（GLB/FBX）+ 骨骼动画
② 只保留一只简化手臂，把预算花在枪上

枪本身也还有差距：真实 AK 有冲压机匣的凹槽、铆钉、木质纹理，
这些用盒子/圆柱拼不出来，只能靠贴图或模型。

# S9.7 · B 方案：把手藏进战术手套

## 1. 为什么放弃"做一只真的手"

程序化几何能做形状，做不出**质感线索**：指节、指甲、皮下血色、手腕的骨点过渡。
一旦露皮肤，观众会立刻盯着那块不自然的肉色看 —— 等于把问题放大。

换深色手套之后，手只需要负责两件事：**轮廓**和**遮挡关系**。
这两件事恰好是几何能做好、而且真正影响观感的。

## 2. 三层材质，缺一不可

```gdscript
glove   (0.175, 0.168, 0.150)  roughness 0.66  specular 0.10   # 手套主体
pad     (0.300, 0.292, 0.268)  roughness 0.46  specular 0.18   # 手背护片
sleeve  (0.062, 0.066, 0.054)  roughness 0.95  specular 0.04   # 袖子
```

- **手背护片**不是装饰。纯深色的手在阴影里就是一团黑，
  一块亮度高一档的平板负责给出明暗分界，轮廓才读得出来。
- **袖子压到最暗**，把手臂推成"暗色背景"，让枪成为视觉主体。

## 3. 卡了我半天的坑：`metallic_specular` 默认值

把袖子 albedo 设成 `(0,0,0)`，画面上它**还是浅灰色**。
改颜色没反应、改纯黑还是灰 —— 最后是靠读 PNG 像素才定位的。

原因：`StandardMaterial3D` 的 `metallic_specular` 默认 **0.5**。
布料/皮革几乎没有镜面反射，但 0.5 会让它**反射整片天空环境**。
一个 albedo 为 0 的物体，照样被环境反射照成中灰。

```gdscript
m.metallic_specular = specular   # 布料给 0.04，橡胶/护片给 0.18
```

**排查方法值得记住**：颜色改了没反应，先别怀疑"是不是没生效"，
去读截图的像素值。人眼对灰色的判断非常不可靠，
而 `(196,255,152)` 这种数值会直接告诉你"这是被环境光染绿的反射光"。

## 4. 手的摆放：三面碰壁的记录

| 位置 | 结果 |
|---|---|
| 护木正下方 | 被护木完全挡住，只剩一根管子的圆头 |
| 护木前端（C-clamp） | 手掌嵌进木头里，画面出现深色缺口 |
| 护木右侧 | 和右手挤在一起，挡住准心 |
| **护木下方 + 往外挪一点** | **不穿模、不出戏，但读不出手指** |

**结论**：在这个相机角度下（枪在右下、相机在右后上方），
左手托护木天然处在视线死角。想让手指清晰可见，
不是调坐标能解决的 —— 需要换一个更低的相机、或者用带骨骼的手部模型。

## 5. 这一版拿到什么

- 有手臂从画面外伸入托枪，不再是悬空的枪
- 手套/护片/袖子三层明暗，手臂不再是一根"塑料管"
- 没有穿模、没有怪异色块
- 枪管平行视线，枪口落在准心正下方

**没拿到的**：手指细节。这一项在程序化几何 + 当前机位下是死路。

# S10 · 战斗闭环：从"打靶"到"会死"

## 1. 闭环缺的是哪几环

S9 结束时能"打靶"，但那不是战斗 —— 靶子不会动、不会还手、玩家不会死，
所以**没有任何理由后退**。压力来自危险，危险得先真的存在。

S10 补上三环：

```
玩家有血 → 丧尸会追会咬 → 死了会重生
```

四件事各自独立，但缺一件闭环就断：
- 没有血：被打没代价
- 没有 AI：血永远不会掉
- 没有前摇：掉血莫名其妙，玩家觉得游戏在耍赖
- 没有重生：死一次就得重启

## 2. 玩家生命值：复用 UI 锁，而不是到处写 `if dead`

```gdscript
GameState.claim_ui("dead")     # 死亡
GameState.release_ui("dead")   # 重生
```

这一行让聊天、商店、开火、建造**全部自动失效**，
因为它们在 S8 就统一成"有 UI 锁就不吃输入"。

如果不用这套锁，就得在五个地方各加一次 `if dead: return`，
而且以后每加一个系统，都会漏掉一次。**这是 S8 那个设计在两年后才开始还债的地方。**

死亡视角也没有用"画面变黑"：
`_death_tilt` 让头慢慢歪倒 + 相机下沉，玩家的直觉立刻知道"我倒了"，
而不是"游戏卡住了"。

## 3. 丧尸 AI：为什么不用导航网格

`NavigationAgent3D` 需要一张 navmesh，而 Terrain3D 生成的地形没有现成的，
要么手动烘焙一大片（慢、且地形改了要重烘），要么自己写寻路。

而是**丧尸本来就该直线冲**。所以：

```gdscript
velocity → 朝玩家的水平方向 × 速度
move_and_slide()          # 撞墙自动贴墙滑行
```

代价是它会卡在凹形墙角。这在"开阔地 + 少量建筑"的关卡里可以接受；
真需要穿门时，再给关键点加路标，而不是上整套寻路。

**速度必须低于玩家冲刺**：丧尸 2.4~3.9，玩家走路 5.0、冲刺 8.5。
跑不过玩家的敌人才有"可以撤"的空间 —— 这是 L4D2 的核心节奏，
如果丧尸比玩家快，游戏就变成"必须站桩清场"。

## 4. 攻击前摇：0.28 秒

```gdscript
_attack_cd = ATTACK_INTERVAL
Sfx.play("zombie_growl")          # 先给声音预警
await timer(ATTACK_WINDUP)        # 0.28 秒后才真正扣血
```

没有这段延迟，近战就是"贴上来立刻掉血"，玩家只会觉得被系统坑了。
有前摇之后，同样的伤害变成"我听到了、我退了、是我慢了一步"——
**同样的难度，体验完全不同。**

前摇期间还要检查一次距离（`ATTACK_RANGE + 0.5` 的容差）：
玩家在这 0.28 秒里后退了，就该打空。

## 5. 丧尸之间要互相排斥

不加这一条，五六只丧尸会精确叠在同一个坐标上，看起来像一只，
子弹也只能打到最前面那只。

```gdscript
if d < SEPARATION:
    velocity += off / d * (SEPARATION - d) * 3.0
```

这是最便宜的"群体感"：没有寻路、没有编队，只是互相推开，
但玩家看到的是"一群东西涌过来"。

## 6. 测试踩的坑：重生后被咬，不是 bug

`--selftest combat` 第一次跑，重生后 HP 是 88 而不是 100。
看起来像"重生没回满血"，实际是**丧尸还守在出生点继续咬**。

这不是代码错了，是测试没考虑"原地重生 = 又回到敌人嘴边"。
修法是在验证重生前把丧尸清掉，而不是去改重生逻辑。

**教训**：测试失败时先问"这是不是被测系统在正确地做一件我没预料的事"，
再问"是不是代码错了"。前者占了相当大比例。

## 7. 这一版的边界

- **没有掉落**：打死丧尸什么也不给。拾荒是 S11 的事
- **没有波次/尸潮**：只有"低于 6 只就补一只"，没有成群的压迫感
- **丧尸不会绕路**：卡在凹墙角时会一直蹭
- **没有声音定位**：只有位置音效，没有"背后有脚步声"的方向提示
- **近战只有一种**：没有扑咬、没有抓取、没有特殊感染者

# S11 · 拾荒与背包：让"打完"变成"去捡"

## 0. 一句话

S10 结束时你能"打"，但打死之后**什么也没有** —— 于是没有理由往深处走。
S11 补上收益端：尸体掉东西、箱子能搜、身上装不下就得做选择。

```
进危险区 → 打丧尸 → 捡物资 → 装不下 → 决定"再深入一点还是回基地"
```

这条线里，**"装不下"是唯一产生决策的环节**。所以背包不是计数器，是玩法。

## 1. 为什么背包用"格"而不是"重量"

重量更真实，但它**不可预估**：捡一块金属是 +0.3 还是 +1.2？玩家算不出来，
于是每次拾取都像开盲盒，压力变成烦躁。

格子是离散的：一眼看到"还剩 2 格"，就知道"还能再拿两样"。
**压力必须可预估，玩家才会真的为它做决策。**

配套的两个细节：
- 同类物资**先填已有的堆**，否则会攒出一背包"各 1 个"的碎片
- 装不下时**部分拾取**：只剩 2 格时捡 10 个 → 拿走 2 个，剩 8 个留在地上。
  返回 `int` 而不是 `bool` 就是为了表达这件事

## 2. 三条权威链路，同一条形状（第三次复用）

```
客户端：interact() / 按键  →  rpc_id(1, "_request_xxx")
服务器：校验距离 → 改账本 → 广播结果
```

S8 的购买是这样的，S9 的开火是这样的，S11 的拾取/搜刮还是这样。
第三次写同一套东西的时候可以确认：**这不是某个功能的实现细节，
而是"多人游戏里所有账本型操作"的通用形状。**

服务器必须校验的两件事：
- **距离用它自己看到的玩家位置量**，不信客户端上报的坐标
  （否则在 2 公里外也能"拾取"）
- **数量由它算**，客户端只能说"我要捡这个东西"，不能说"给我 999 个"

还有一个容易漏的：**`_taken` 标志**。
没有它，两个人同时按 E 会各拿一份 —— 这是最朴素的"重放攻击"。

## 3. 弹药为什么不进背包格

这是我刻意做的一个取舍，值得说清楚：

**弹药直接进枪的备用弹，不占背包格，但有上限（240 发）。**

- 弹药是"一直在消耗"的东西，让它占格等于**惩罚玩家带弹**，
  结果所有人都只带一个弹匣下场，游戏变成了"背着一堆材料却打不动"
- 背包的压力应该来自"囤哪些材料"，不是"要不要带子弹"
- 上限的存在才是压力：**攒得起来，但攒不满**，打光了必须出去找

顺带把开局备用弹从 240 降到 90（3 个弹匣）——
240 是"永远打不完"的量，那样拾荒就失去了最强的一条动机。

## 4. 死亡的代价：材料损失一半

| 方案 | 问题 |
|---|---|
| 清空背包 | 一次失误抹掉半小时成果，是惩罚玩家而不是制造张力 |
| 完全无损 | "往深处走"没有任何风险，玩家会一路莽到底 |
| **材料损失一半** | **疼，但不至于想关游戏；而且惩罚的正是"贪心"** |

曲线是设计出来的：材料带得越多，一次死亡丢得越多。
急救包和弹药不损失 —— 那是保命的东西，不该让人"越打越弱"。

## 5. 五个坑

### 坑一：动画不该拥有节点的位置

掉落物要做"上下浮动"，我第一版写：

```gdscript
var _base_y := 0.0
func _ready(): _base_y = position.y
func _process(d): position.y = _base_y + sin(t) * AMP
```

结果所有掉落物都沉到地形以下，截图里一个都看不见。
原因：`_base_y` 是在 `_ready` 里记的，而那时节点**还没被摆到正确高度**（y=0），
于是每帧都把整个节点拉回 0。

正确做法：**只浮动子网格**。

```gdscript
_mesh.position.y = 0.16 + sin(_float_t) * FLOAT_AMP
```

一句话：**位置属于"谁创建了它"，动画只能改自己的子节点。**
这条规则在枪械摇晃、丧尸走路摆动上都成立。

### 坑二：算高度要问地形，不能拿玩家的脚凑

截图脚本里我把箱子放在"玩家位置 - 1.15 米"。出生点前方是上坡，
那个高度比真实地面低半米，东西直接被埋进土里。

**永远用 `terrain.height_at(x, z)`** —— 这不是"多此一举"，
是在维护"地形高度只有一个真相源"这条契约。

### 坑三：改 `signal` 的参数，要改所有 emit 点

给 `GameState.notify` 加了第二个参数 `secs`（不同消息的阅读时长差很多：
"背包已满"半秒够，"搜到：布料 ×2、废金属 ×3"要三秒），
结果忘了每处 emit 都要跟着改，运行时直接报
`Method expected 1 argument(s), but called with 2`。

教训：**信号签名是接口**，改它等于改所有调用方。

### 坑四：断言不能只看"背包格子变多"

容器自检第一次"失败"：占用格子 0 → 0。
排查半天发现 —— 那次抽到的是**弹药**，而弹药是直接进枪、不占格的。

**这不是代码错，是断言写错了。** 正确的断言是
"物品件数 + 备用弹发数"两项之和 > 0。

这和 S10 那次"重生后 HP=88 不是 bug"是同一类错误：
**测试失败时先问"这是不是被测系统在正确地做一件我没预料的事"。**

### 坑五：视角角度要算，不能猜

自检要验证"射线能选中箱子"，我凭直觉给了 27° 俯角，
射线从箱子上方飞过去了 —— 相机在胶囊上方 1.6 米，箱子在 1.4 米高的地上，
2.4 米外的真实俯角接近 **48°**。

正确写法是先转 yaw 面向目标，再用**相机实际位置 → 目标点**算：

```gdscript
var pitch := atan2(aim_at.y - cam.global_position.y, flat_distance)
```

## 6. 顺手修掉的一个老 bug

`_damage_rpc` 在 `amount == 0` 时也会触发受伤红边 —— 而 `amount == 0`
正是"重生"和"用急救包"的调用方式。所以之前**每次重生都会闪一下红光**，
玩家会以为"我回血的时候又被打了一下"。

修法是一行 `if amount > 0.0:`。这类 bug 的特点是：
**它不报错、不影响功能，只是让玩家觉得"哪里怪怪的"。**

## 7. 新增自检：`--selftest loot`

```
tools/Godot.app/Contents/MacOS/Godot --headless --path game -- --solo --selftest loot
```

七项，覆盖从数据到手感：

| 项 | 期望 |
|---|---|
| 走到掉落物旁按 E | 背包 +5，掉落物消失 |
| 只剩 2 格空间时捡 10 个 | 实际拿到 2 |
| 12/12 满时再捡 | 拿到 0 |
| 搜刮容器 | 有收益，`looted=true` |
| 二次搜刮 | 收益为 0 |
| 捡 500 发弹药 | 进枪 240（上限），背包占用不变 |
| 阵亡 | 材料减半，急救包不动 |
| **真实瞄准链路** | **AimRay 识别到箱子，提示"按 E 搜刮「木箱」"** |

最后一项最重要：前面几项都是直接调 `interact()`，跳过了交互探测。
但玩家实际走的是 `AimRay → _target → 按 E`，而"射线打不到"恰恰最容易出错
（碰撞层、reach、相机位置任一写错都会中招）。

## 8. 这一版的边界

- **没有基地仓库**：所有东西都在背包里，装不下就是装不下，没有"存起来"
- **材料暂时没用**：废金属/木材/布料还不能用于建造（S12 才接）
- **没有负重/移动影响**：装满 12 格仍然跑得一样快
- **容器固定 8 个**：位置固定（这是有意的，可学习），但不随游戏进程刷新
- **箱子不能搜第二次**：一次性，也不补充
- **联机时掉落物还没接 MultiplayerSpawner**：单机完全正常，
  开联机那天需要给 `Loot` 容器挂一个同步器（和 `Zombies` 一起补）
